# Translations

Every string the apps show comes from the shared Silo translation catalog
(`Silo-Server/silo-translations`). The same English message is translated once
for every Silo client. This page covers the Android side. The catalog's README
covers keys, message rules and how to add a key.

## Where strings live

- `android-shared/src/androidMain/res/values*/strings_catalog.xml` holds the
  generated strings and plurals, one directory per shipped language.
  `android-shared/silo-locales.properties` lists the shipped languages per app.
  Both are generated: never edit them by hand.
- `.silo-translations` records the catalog version they came from, and
  `.silo-translations-files` lists every generated file.
- Read them through `org.siloserver.silo.common.R`, imported as `CommonR` in the
  phone and TV apps: `stringResource(CommonR.string.common_cancel)`.
- The apps have no hand-written `strings.xml`. An app resource with a generated
  name would hide the catalog's text and its translations, so
  `CatalogSourceTest` rejects one.

A catalog key maps to an Android name by turning `.` into `_`:
`home.section.continueWatching` becomes `R.string.home_section_continueWatching`.
Placeholders are positional (`%1$s`, `%1$d`) in the order the key's
`placeholders` declare them.

## Shipped languages

A language ships once the catalog has translations for it. Both apps set
`androidResources.localeFilters` from `silo-locales.properties`, and
`generateLocaleConfig` builds the system language list from it. The App
language picker lists the same languages (`AppLocales.shipped`). Language
splits are off in the app bundle, so every shipped language is installed.
Debug builds add the `en-XA` and `ar-XB` pseudo-locales.

## Adding or changing a string

1. On a `silo-translations` branch, add the key to `catalog/en.arb` with a
   description, then run `make fmt` and `make check` (see that repository's
   CONTRIBUTING).
2. In this repository, run
   `scripts/sync-translations --platform android --local <silo-translations checkout>`.
   Once releases exist, use `scripts/sync-translations --version <release>`.
3. Use the new name in code, and commit the generated files with the change.

`scripts/check-translations` confirms the committed files match a fresh
generate of the recorded version. CI runs it on every pull request and push.

English stays byte-identical while strings move into the catalog: change the
wording only in a separate change.

Only text a user sees is translated. Text that is stored (Room, preferences,
WorkManager input), sent (to the server, to a TV over Remote Control) or
matched against stays English in every language. When the same message is
both shown and sent or logged, show the catalog string and send its English
from `EnglishText.string(id, …)`, or the server's own `ApiResult.Error.detail`.

A count that a user can set, or that can pass 999, goes into a plural as a
separate text placeholder (`{count_text}`, passed as
`LocaleFormat.integer(count)`) instead of `#`, so it is never grouped.
A collection card's count, the TV Browse grid's title count, and a person
page's title count use `LocaleFormat.groupedCount(count)`
(`UiText.GroupedCount` in a shared model) instead, which adds the locale's
thousands separator ("1,284 titles", "1.284 Titel").

## Dates, times and numbers

`common/i18n/LocaleFormat.kt` formats for the applied app language. Each call
reads the current language, so nothing goes stale after a change.

- `LocaleFormat.locale()` is the formatting locale: the device's own locale
  when it speaks the chosen language (an `en-GB` device that picks English keeps
  day-month order), otherwise the chosen language. A device language without a
  catalog formats as its stand-in (see the last item). In composition use
  `currentFormatLocale()`, and key any `remember` that formats on it.
- Dates and times use a skeleton, `LocaleFormat.dateFormatter("yMMMd",
  "MMM d, yyyy")`, never a fixed pattern. Each language gets its own field
  order and digits; US English prints what the old pattern printed.
- A number passed to a `%s` placeholder goes through
  `LocaleFormat.integer(n)` (no grouping, the language's digits), never
  `n.toString()`. In a model that a screen draws later, pass
  `LocaleInteger(n)` and format it when drawn.
- Decimals for display use `LocaleFormat.decimal` or `String.format` with
  `LocaleFormat.locale()`; clock-style durations use `LocaleFormat.clock`.
- Language names and other words built in code use
  `LocaleFormat.interfaceLocale()`, the language the text is in.
- Text that is data keeps `Locale.ROOT`: ids, CSS, wire formats, case folding
  and diagnostics.
- A language without a Silo catalog is never shown or formatted (D64). When the
  device's language has none, `AppLocales.wrap` (each activity's
  `attachBaseContext`) gives the activity English resources, or the first
  shipped language in the device list, and `LocaleFormat` formats in it too. So
  `%d` placeholders, plural rules, layout direction and `LocaleFormat` agree
  until the language ships. An activity whose locale `wrap` fixed recreates
  itself on an in-place language change (`AppLocales.needsRecreate`).

## Server text

- **Section titles.** A home or library row's `title_key`/`title_args` name a
  catalog message. Show rows with `sectionTitle(section)` (composable) or
  `context.sectionTitle(section)`, never `section.title` directly. A renamed row
  has no key and keeps the title as typed.
- **Problem details.** `ServerText.install` (called from each `Application`)
  makes v2 errors' `ApiResult.Error.message` show `error.field.<code>` or
  `error.<type>` in a translated interface. English always shows the server's
  `detail`. Code that recognises a server error reads `ApiResult.Error.detail`
  or the `error` code, never `message`.
- Names and titles inside a message use `stringResourceWithNames`, which
  isolates them in a right-to-left interface.

## Converting a directory

Each extraction change converts one package group. When a directory has no
literal text left, add it to `convertedDirectories` in
`android-shared/src/androidUnitTest/.../i18n/CatalogSourceTest.kt`. From then
on a new `Text("…")`, `text = "…"` or `contentDescription = "…"` literal there
fails the unit tests. A literal whose letters all sit in `$name` or `${…}`
templates (`"$label, $value"`) only joins translated text and passes. Put
`// i18n-ignore` on a line that must stay literal, such as a brand name.

A view model never holds translated text: it would keep the old language after
a change. It holds a `UiText` (`org.siloserver.silo.common.i18n.UiText`): the
server's own words (`UiText.Raw`), a string resource (`UiText.Res`, or
`uiText(id, …)`), or a catalog string the shared module names (`UiText.Key`,
`UiText.Plural`). The screen shows it with `text()` (`text(context)` or
`text(resources)` outside composition). `String` arguments are isolated in a
right-to-left interface. `result.errorText(fallback)` is the catalog form of
`errorMessage(fallback)`.

Check a converted screen with the `en-XA` pseudo-locale. In a debug build, pick
`en-XA` (or `ar-XB`) in Silo's App language setting while the profile has no
language of its own; it applies on that device only and is never saved. This
works on Android TV and on phones whose system settings list no pseudo-locales. Converted text shows accented and padded
in brackets, and anything still plain English is still hardcoded.

## Text from the shared module

The `shared` module can't read Android resources, so it names catalog strings
instead of building English. `UiText` itself lives in `shared`
(`shared/.../common/i18n/SharedUiText.kt`), in the same package as the
android-shared resolvers, so shared and app view models hand screens one type.

- **Shown text** in a shared view model or model is a `UiText`:
  `UiText.Key(SharedString.X, listOf(args…))`, or
  `UiText.Plural(SharedPlural.X, count, listOf(args…))`, where `count` picks the
  form and fills `{count}` and `args` fill the placeholders after it (a
  `{count_text}` slot takes `UiText.Number(count)` first). A key that declares
  another placeholder before `{count}` (`{played} / # watched`) names its
  position with `SharedPlural`'s `countIndex`. Never a `String` field with
  English in it; a field typed `UiText?` rejects a literal.
- **Numbers, dates and language names** are values the screen formats with
  `LocaleFormat`, as the app's own numbers and dates are (see "Dates, times
  and numbers"):
  - `UiText.Number(n)` for a number in a `String` placeholder or shown alone.
    A whole number is `LocaleFormat.integer`: the interface language's digits
    without grouping (D55), so English keeps "1234" and Arabic shows "١٢٣٤".
    `minIntegerDigits` pads ("S01E02"). With `maxFractionDigits` it is
    `LocaleFormat.decimal` in the formatting locale ("1.5 Mbps").
  - `UiText.GroupedCount(n)` for a count with the thousands separator
    (`LocaleFormat.groupedCount`), only where the section above allows it.
  - `UiText.CalendarDate(year, month, day)` for a date with the month as a
    word, in the formatting locale's order ("Jan 5, 1980" in US English).
  - `UiText.LanguageName(tag)` for a language's name in the interface
    language, never a hand-written English table.
- **Pickers** select by value or by `UiText` equality, never by comparing
  resolved label text, so a translated label can't change the selection.
- **Outcomes** that code branches on, or a fixed set of messages, are a sealed
  type or enum with a `text: UiText` next to it, as `PasswordChangeError` and
  `NotificationsError` do. Build one from a result with `of(result)`, following
  `PasswordLoginFailure.of(code, problem)`. Tests assert the type, not its text.
- **Server text** stays `UiText.Raw`.
- **Errors.** Screens show `result.errorText(fallback)`, never
  `ApiResult.Error.message`. It returns, in order: the error's `text`, the
  server's message (a v2 problem's detail, translated per D33 when it arrives),
  `fallback`; and the network or timeout text for a request with no answer.
  `errorTextOrNull()` returns null instead of a fallback.
  - An error the app builds gives `ApiResult.Error(code, error, message,
    text = UiText.Key(…))`. `message` stays English for logs. Codes are not
    unique per message (`identity_changed` has several), so the text belongs to
    the place that builds the error, not to a table of codes.
  - Code that passes an error on returns the same object (`is ApiResult.Error ->
    r`), so `text` and `detail` survive. Replacing the wording means replacing
    both: `copy(message = "…", text = UiText.Key(…))`.
  - Code recognises an error by `code` and `error`, never by `message`.

### Adding a shared string

1. Add the key to the catalog, or reuse one with the same English and meaning
   (widen its `x-platforms` to `android`); Apple keys for the same screen often
   exist already. A plural's first placeholder is `{count}`; add
   `{count_text}` only for a count that can pass 999 (see above).
2. Regenerate (see above).
3. Add an entry to `SharedString` (or `SharedPlural`) in
   `shared/.../common/i18n/SharedString.kt` with the catalog key, and its row in
   the `when` in `android-shared/.../common/i18n/SharedStrings.kt`. The `when` is
   exhaustive, and its static `R` references keep the string through release
   shrinking. `SharedTextTest` checks that each row names the resource its key
   generates. It doesn't check placeholders: pass arguments in the order the
   key declares them.

Text that is data stays English (D44): what the shared module logs, sends,
stores or compares keeps its English constant (for example
`PASSWORD_CHANGE_REQUIRED_MESSAGE`), next to the `UiText` a screen shows.

In `commonTest`, compare `UiText` values (`UiText.Key(SharedString.X, …)`); they
need no resources. A test that checks the English a screen shows calls
`english()`, which formats the text from the generated English
`strings_catalog.xml`. Android tests that check English resolve with
`text(resources)`.

When an existing key's placeholders can't be filled in `UiText.Plural`'s order
(the count first), return a small sealed type and word it in android-shared
instead, as `WatchPartyPresence` does.
